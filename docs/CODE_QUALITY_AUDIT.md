# Code quality and resource audit

12 November 2026. Local working tree, during milestone 3A. This is a scoped source audit and controlled measurement, not a security certification or a complete load test. Existing milestones 1A, 1B and 2 remain accepted within their documented boundaries. No dependencies, services, agents or infrastructure architecture were added.

## Changes justified by evidence

| Finding | Severity / impact | Action and regression risk |
| --- | --- | --- |
| Conflict review read every document's text and every archived identifier, even for one two-source conflict | High memory/transfer amplification; measured 5,127,377 serialized SQL-result bytes per check in the baseline fixture | Read referenced source metadata/version only; fetch text solely for legacy sources without hashes, and archived IDs only when referenced. Preserve owner predicates, stale revision checks and audit payloads. Regression covers legacy hashes and exclusion of unrelated text. |
| SQLite named retrieval filtered after loading all documents and vectors; grouping scanned all chunks for every document | High for laptop memory; 6,636,422 result bytes for one selected document in baseline | Push document IDs into both SQL reads; group once in a map; compute a missing version hash once per document. Preserve full-library exact retrieval and ordering. Regression checks unrelated and other-account content never crosses the SQL boundary. |
| Chunker searched the entire prefix for a newline at every boundary, although early newlines were unusable | Medium CPU amplification; newline-free 500k-character baseline p50 92.00 ms on this host | Search only the usable boundary window. Golden hashes preserve exact previous passage layouts for long prose, table rows and boundary cases. No reindexing or embedding identity change. |

See [PERFORMANCE.md](PERFORMANCE.md) for before/after measurements and their limitations. Failed reproduction logs are `data/performance-regression-before.log` and `data/performance-scope-before.log`. Chunking was a measured inefficiency, not a changed-output defect.

## Reuse, duplication and lifecycle review

- Reused `SqlStore` owner-scoped SQL/transactions, `historyCursor` validation, temporal metadata, runtime verification schemas, provider deadlines, durable ingestion checkpoints and existing fixtures. Additive history endpoints use the same authorization and DTO validation as existing API routes.
- Retrieval's dense and lexical database paths intentionally differ. Their similar row-mapping code does not justify merging different candidate/compatibility semantics in an unrelated refactor.
- No dependency removal or dead-code deletion: a complete static/runtime usage proof was not established. Exported lifecycle UI components have planned consumers in milestone 4; they are unfinished integration, not proven dead code.
- `DatabaseService` extends `KnowledgeStore`; the latter imports only the `StoredDocument` type back. That type-only dependency is erased at runtime. No new Nest provider cycle introduced.
- `SqlStore` releases PostgreSQL clients in `finally`, caps each pool at five connections, bounds connection/query waits and closes pools. Aggregate API-plus-worker pool demand still needs milestone 6 testing.
- Ingestion/revalidation have single in-process tick guards, abort controllers and shutdown hooks. The future separate worker/queue has not been implemented. Do not claim queue shutdown/retention is already proven.
- PDF parsing destroys its parser in `finally`; production parser isolation has a 20-second timeout and a 96 MiB V8 heap cap. That cap is not a total RSS cap. Upload buffers and IPC copies still count toward memory.
- Existing timers/caches are bounded or shut down in the inspected paths. No leak was proven by inspection. Short before/after heap samples do not replace a repeated-load soak test.
- Existing RAG execution records model stage, model name, duration, success and nullable provider token usage. Supported answers avoid repair; targeted retrieval is limited to one additional round, and repair attempts to at most two. All changed claims still undergo verification. No provider-stage bypass was introduced to improve timings.

## Release gate

Milestone 3A is accepted within its controlled boundaries; implement 3B next. Add the performance evidence required by each remaining milestone, then run a final optimization/soak audit at milestone 7. A green small regression suite does not establish large-library memory safety, live factual accuracy, throughput, or cloud readiness.

## Milestone 3B follow-up (13 November 2026)

The preceding audit is the historical 3A checkpoint. The separate-worker slice adds a thin BullMQ adapter and pinned supported driver, reusing existing ingestion/revalidation processors and SQL fences. No second parser, verifier, job schema or backend image was introduced. Queue payloads carry IDs only; dispatch and processing are bounded independently. The legacy node-redis admission client remains in place to avoid an unrelated authentication/concurrency rewrite.

See [MILESTONE_3B_RESULTS.md](MILESTONE_3B_RESULTS.md) for final tests and resource observations, and [BACKGROUND_WORKERS.md](BACKGROUND_WORKERS.md) for role/shutdown/queue contracts. Soft queue admission across simultaneous dispatchers, aggregate connection capacity, provider costs and sustained throughput are explicitly unproven. Lease-loss cancellation for foreground API work remains a release gate; the revalidation processor has its own aborting SQL heartbeat.

## Milestone 3C follow-up (14 November 2026)

Targeted changes reuse the existing version store, event pager, temporal retrieval, strict verification contracts and SQL processors. Citation rendering is deterministic and adds no inference call; unchanged assessments avoid redundant version payloads. Latest-assessment lookup adds one bounded indexed read per revalidation. Existing job rows and knowledge events support retries/audits without a migration or new service. No live latency/token savings are claimed. Final regression evidence and residual UI/load gates are in [MILESTONE_3C_RESULTS.md](MILESTONE_3C_RESULTS.md).
